# Rule: Multi-Agent Orchestrator Discipline

Trigger: delegating work to another bot, convening a meeting, waiting on a completion, asserting a bot's state/identity, any moment of multi-agent coordination. (Codified as a written rule per the operator's directive, dated 2026-05-16.)

> Diet note (2026-07-31): incident narrative compressed; every clause, caveat, and forbidden path preserved in full. Original wording lives in version-control history.

## 1. Bot identity = verify, never guess
- Bot-identity source of truth = the `<bot>` name a session-start hook injects as `=== [<bot>] soul.md ===` (derived from `▶ Fill in: your bot-identity env var, e.g. DISCORD_STATE_DIR / ~/.claude/channels/discord-<bot>`). Any shared/root config's bot-specific working-directory metadata is only that bot's own identity when `<bot>` matches it — if it doesn't match, ignore that block.
- Before delegating to or waiting on a teammate bot, the orchestrator must **verify the target bot's actual session state** (tmux list/capture, source-fact check). Assuming "it's probably still working" and passively waiting counts as dereliction of duty (regression logged 2026-05-16).

## 2. Never wait — always re-activate (collaboration boundary)
- If a teammate bot is a gate and is idle/blocked → **actively re-activate it**: run any non-gating parallel tracks yourself first, and **re-send via your external channel (e.g. Discord)** to wake it.
- ⚠️ **Never inject input into a peer bot's session via `tmux send-keys`** (rule dated 2026-05-28): this makes the target bot treat the input as coming from "a sender and time unknown" — a loss of provenance equivalent to an internal prompt injection. tmux is for **read-only capture only**; signaling/re-activation goes through a **single external channel** (e.g. Discord). After re-sending, **5+ minutes with no response** permits a wake-only tmux keystroke (internal code: R8); if still no response, treat it as a bridge/connectivity problem (do not work around it) and escalate to the operator. Sending *content*-bearing input via send-keys is an emergency measure reserved **for the operator only** — the orchestrator is itself just a peer bot, no exception for it. Sending the human's own session meta-commands (e.g. `/compact`, `/clear`) is a normal, everyday exception. Details → [discord-comms](discord-comms.md) §5, codes R5/R7/R8.
- Distinguish: **a block that needs a user decision** = report status, then stop (no polling — see [autonomy](autonomy.md) §3) vs. **an idle teammate** = re-activate and verify. Do not conflate the two.

## 3. Meeting coordination — never decide alone
- When convening a meeting, the orchestrator must not impose its own framing — instead adopt each participating bot's own domain prep document as that domain's source of truth.
- LOCK sequence = (gate teammate's output → meeting consensus → independent review by a rescue/verification subagent → two-track review by your codex-family bot → the operator). No solo skipping of any step.
- **Meeting-trigger classification** (regression correction dated 2026-05-21): any orchestrator-initiated multi-bot dispatch — formal or informal — counts as a **meeting** → create a dedicated thread plus the standard 4-file document set. Self-check right before dispatch: "2+ bots, or 30+ minutes?" → if yes, create the thread first.
- **Dispatch messages must state the thread id explicitly**: e.g. "speak only inside thread `▶ Fill in: <thread-id>`" — omitting this lets replies fall back to the default channel/completion thread, a your deployment's channel-governance rule §2 violation cascade.
- **Opening a meeting thread requires launching a companion watchdog**: `▶ Fill in: <your watchdog script>` `start <thread_id> --goal <completion-condition> --tasks-total <N>`, plus a roughly-5-minute periodic ticker (your OS scheduler). **Fail-closed**: a live meeting must never be false-terminated — a corrupt or missing state file means "still active," not "done." Progress is pushed via heartbeat. Ticker registration = your schedule-bot's domain. See your internal orchestrator-watchdog design spec, dated 2026-05-16.

## 4. Communication integrity
- Split messages: **re-insert the mention in every part** — omitting it causes a silent drop. → [discord-comms](discord-comms.md) §2
- Before mentioning a bot, use its **real roster user id** — never guess or invent a name.

## 5. Bot dispatch = state the HOW fully in the first message (hard rule — operator directive dated 2026-06-07, logged as "a clear communication failure")
Giving the WHAT without the HOW causes bot drift → incremental-correction churn (each correction round costs one full bot turn).
- **Self-check right before sending**: "Can this message *alone* be executed correctly — tools, parallelism, and forbidden paths included?" → if no, fill the gaps before sending.
- **Dispatching image-generation work to your codex-family bot**: (a) either parallel subagents or sequential built-in calls (the bot's judgment) (b) **calling the built-in image-generation tool directly is the correct, key-less path** — one call per asset, no batch/`n` parameter. **Forbidden paths, stated explicitly**: ad-hoc CLI fallback scripts, raw API-key environment variables, unapproved image models, and any wrapper that skips verification. **Narrow exception (dated 2026-06-22)**: when file materialization is the actual completion condition for a multi-asset deliverable (e.g. a slide deck), a verified wrapper script is allowed — success condition = the freshly generated images' checksums are unique across this run's source files and slugs don't collide; on failure, do not record it in the manifest. The built-in image-gen tool itself is not forbidden (correction dated 2026-06-13 — an earlier version of this rule had that backwards).
- **Built-in materialization hard gate (dated 2026-06-22)**: for multi-image dispatches, the first message must state "only new images created after the dispatch timestamp; verify with file-type/metadata/checksum tools; a checksum collision across slugs = stale-cache FAIL; do not record it in the manifest." Trust the actual file over a "rendered" claim in text.
- Regression example: a 2026-06-07 illustration-dispatch incident — a missing HOW caused **7 rounds** of method drift, requiring **7 rounds** of operator correction.

## 5.5 Non-trivial debugging = co-engage your codex-family bot (operator directive dated 2026-07-11)
- On any **non-trivial debugging** task, bring in your codex-family bot (`▶ Fill in: <its roster id>`) to participate — the discovering bot must not close it out solo. Shape: ① independent reproduction/diagnosis ② cross-review of the proposed fix ③ parallel fixing. Dispatch per §5 (state the HOW), and **verify the machine boundary right before dispatch** (correction dated 2026-07-20: an earlier assumption that this bot ran on a remote machine was stale and caused a blocked regression — it in fact runs in a local tmux session on a specific machine). Machine-local work = an isolated clone at `▶ Fill in: <your isolated-clone path convention>` — never modify another bot's primary working tree directly.
- **Trivial escape hatch**: a typo or a one-hop, self-evident fix may be handled solo (bar set by [code-quality](code-quality.md) §6) — note the judgment call in one line in your progress log/commit. Case-by-case judgment and the operator's final call apply (see [skill-process](skill-process.md) §6). Re-design this section if/when a dedicated debugging/security bot is introduced (operator directive).
- **Security-domain assignment** (operator standing directive dated 2026-07-13, scope-corrected same day at 08:01): **new security work** (integrity checks, sealing, tamper detection, adversarial audit) defaults to the codex-family bot line (your dedicated security bot, once you have one) as owner. Non-security work (feature verification, experiment bodies) stays with your regular bots. **Do not force-migrate an in-progress track that is working well** (operator correction — "overapplied"; the new-work-assignment rule takes priority, and retroactive reassignment needs a one-line operator confirmation). The orchestrator does not re-derive security verdicts itself — coordination only. Case-by-case judgment and the operator's final call apply.

## 6. Pre-empt teammate-bot context exhaustion (internal code: P2 — pattern #3 from a prior harness-synthesis review)
- Right before dispatching a new, complex task, check the target bot's remaining context (read-only tmux capture, or self-report — `send-keys` remains forbidden). **If headroom is low (≲15%), hold the dispatch** → instruct it to clean up first (report to the operator if a context-compact is needed — see [discord-comms](discord-comms.md) §5, code R5) → re-dispatch in the order "clean up → re-read the source of truth → begin." Don't let it run out mid-task and clean up after — heading it off is cheaper. This is a rule-level (manual) gate; an automated hook is a separate matter. Case-by-case judgment and the operator's final call apply.

## 7. Scheduled/deferred execution = re-check the ledger right before executing (dated 2026-07-25, harness-audit — a stale-dispatch regression)
- **An instruction deferred via a schedule (cron, reminder, queue) is a snapshot of the entire instruction as of registration time** — there is no guarantee the premise at registration time still holds at execution time (not just one value goes stale — the whole scope of the action can). **Re-checking the relevant source of truth's tail (e.g. your progress log) is mandatory right before execution**: if a correction, cancellation, or resolution has since been logged, hold execution and report instead (holding is the normal branch, not an exception).
- When registering a scheduled item, **record an as-of timestamp (the instruction's registration time) in the payload**. Mechanizing this (a pre-execution delta check) is your schedule-bot's domain to design (implementation is a separate item).
- Regression case (internal case id: gamsgo1, 2026-07-25): a scheduled instruction registered at 13:04 was resolved at 15:00 and logged as cancelled at 18:05; without a re-check it was still executed at 19:00 — a stale-credential dispatch (a downstream rejection gate caught the damage before it landed). Case-by-case judgment and the operator's final call apply (see [skill-process](skill-process.md) §6). → see your harness-audit outcome log §5.

## 8. Never close it out alone — cross-process review (internal code: G3, dated 2026-08-05, on the operator's go-ahead)
- **Trigger formula = (how hard to reverse) × (how far it reaches) + a bonus term for authority labels** — a label is a reinforcing add-on, not a precondition: recipients read it as authoritative even when you didn't mean to label it that way. Concretely: pushing to a public repo · a factual statement inside a report to the operator · asserting "doesn't exist / unsupported" · **a prescription, coordinate, or verdict another bot will execute without re-verifying it** · issuing a "clean / reviewed / final" label. **Explicitly excluded: observational reports** (liveness pings, schedule alerts, status relays).
- Form = one cross-check by a **different, explicitly-named** bot before sending. **Bidirectional** — a reviewer's or fixer's own output also gets reviewed (a one-way gate is a blind spot for the reviewer itself). If no reviewer is available, context is critically low (see §6), or a deadline is imminent: **send anyway, but explicitly note "cross-check not performed (reason)"** — the goal is preventing unreviewed work from silently looking reviewed, not blocking delivery.
- **Direction of the cross-check = "attack his claim with your own data"** (a convergence point two review bots reached on 2026-08-05) — not opening someone else's data on their behalf (this doesn't conflict with a no-ghost-writing-a-census rule: the verifier disproves the other's hypothesis using *data they themselves can access*; demonstrated case — one bot rejected another bot's hypothesis using its own transcript). What the cross-check covers = **comprehension** (did they actually read it, and does the reasoning hold) — a forced/automated gate only reaches **access** (did they open it, cite it, use the right format); a wrong citation or a paraphrased copy sits outside a mechanical gate's reach (triple-demonstrated).
- **State the disproof coordinate explicitly** (a refinement contributed from the writing-bot side): when publishing a hypothesis or a prescription, **also state whose data, and which data, would disprove it** — otherwise the cross-check dies in a "not my data" vs. "that's your domain" standoff (demonstrated same day: only the hypotheses with an explicit coordinate got disproven promptly; a figure without one sat unchallenged because it belonged to the person who published it, and the error propagated into a later argument — internal code: S4).
- A "pre-review" label **must travel with the content whenever it's quoted or reused elsewhere**. The reason a cross-check should precede even your own self-check (re-measurement, comparison against the source) — a false negative in your own suspicion (simply not suspecting your own work) is structurally something only someone else can catch — demonstrated case: across four bots' detection paths, cross-checking dominated while self-detection was near zero (internal code: S1).
- Coverage relationship: an automated copy-coherence gate (internal code: G1) cannot catch a **paraphrased copy** (below the verbatim-match threshold) — this cross-check step is what catches that. It is not an optional add-on beyond budget; it is a required layer implied by G1's own coverage definition.
- Case-by-case judgment and the operator's final call apply (see [skill-process](skill-process.md) §6). → see your internal harness-improvement plan, section G3, and its integrated-findings document §3.
