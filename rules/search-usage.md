# Rule: Knowledge-search usage (GraphRAG-style search + generic fallback) — shared across bots (performance + time)

Trigger: about to search vault/knowledge-base content; right before calling your primary semantic search, a full-text CLI, or any generic search tool; immediately after a search fails or comes back empty.

> Why: an audit of live search-server traffic on 2026-06-11 (366 sampled queries) found bots converging on MCP default settings without picking a mode, retrying the identical query 9 times in a row with no backoff, and a stale "use the CLI first" instruction that had been injected into every bot's context — a drift nobody had caught. This rule is that audit's fix (labeled G-1 below) plus its own update rule (G-3). Which search tool to reach for at all is decided elsewhere — see your deployment's vault-ops rule §3; this rule is about using the tool you picked well, once you've picked it.

## 1. Query construction (performance)
- **Natural-language, keyword-form, 3-7 words** is the best-performing band (366-query sample averaged 5.3 words). Full sentences padded with function words/particles — do not do this.
- Trust the defaults: hybrid mode, top_k 10, and rerank on are already the tool's tuned defaults — **do not hand-tune weights or mode**. (The audit observed bots attempting manual weight overrides; it had no effect except polluting the cache.)
- For rare proper nouns (product-style names, e.g. domain-like strings) or exact phrases, on a first miss retry **once** with a spelling/alias variant (native-language form vs. transliteration) — do not just re-throw the same query.

## 2. Failure and retry discipline (time)
- **No consecutive retries of the identical query** (the regression this fixes: the same query re-thrown 9 times in a row with no backoff). One failure or empty result = branch immediately:
  1. Rephrase the query once (swap words / shorten it) →
  2. **Fall back to your secondary full-text CLI search** (tier 2 — note: no relevance ranking, so use a large limit and isolate keywords) →
  3. Generic search (grep/find).
- **🚨 Before asserting "not in the knowledge base / empty / no such record" = one mandatory absence-verification lookup pass is required** (introduced 2026-06-29 as a hard, enforced fix): rare proper nouns (product, person, or tool names) get semantically "buried" by meaning-based search, producing a **false absence**. The absence-verification pass should combine exact-match full-text search (tier 2) with an unrestricted grep across the full corpus (not just a truncated/head-limited one, and covering both the working copy and any live/deployed copy) — **run as a single automated command**, not a manually-chained cascade a step of which can get skipped or truncated. Only a genuine zero from that pass — and only after one spelling-variant retry — justifies declaring absence. Regression precedent (2026-06-29): two named entities were wrongly declared "not in the vault" using semantic search plus a grep whose output had been silently truncated, when in fact multiple matching records existed; the same session had a second, structurally identical failure elsewhere the same day — "incomplete observation → absence claim," twice. Evidence was archived to a dated incident report in the bug-report archive.

▶ Fill in: the concrete command for your tier-2 exact-match CLI and the concrete command/script for your absence-verification lookup pass (exact-match search + full untruncated grep, single invocation).

- Server timeout (>10s) or HTTP 5xx = **report/log it right where it happened, then fall back** — do not poll waiting for the server to recover.
- Time expectations (measured, post-cleanup): readiness check (`/ready`) ~2ms · warm search ~0.2s · cold search ~1.5s · warm-up right after a server restart ~25s. Outside this range is a system-health signal — report it, don't just retry.

## 3. Guidance source-of-truth and update rule (G-3)
- The source-of-truth for *which* tool to reach for is **your deployment's vault-ops rule §3** (recall of content → semantic search first / exact match or structure → CLI / code or forensic lookup → generic search). If this rule, memory, or a persona file disagrees with §3, **§3 wins** — fix the disagreeing document the moment you notice, and log it in your progress notes or memory the same way this kind of fix normally gets logged.
- When the search infrastructure itself changes (server, channel, weights), update this rule's time-expectations and defaults section **in the same PR/session** as the infra change (stale guidance here is how the cross-bot "CLI first" drift happened in the first place).
- **Index source-of-truth path resolution — a worked incident, illustrative (fixed 2026-07-26)**: on one occasion the vault path used by the indexing pipeline was set by an environment variable that, when unset, fell back to a stale code-level default. That variable only affected the *index-update* code path, not the *live search* code path — so "search results are stale" and "the index-update path is using a stale default" are two different failure modes, not one. A sibling component already had the correct default — the stale-default fix had been applied in one place without checking for the same latent bug elsewhere. The fix (updating the code-level default) did **not** take effect on the already-running process, because the constant was evaluated once at module-import time — editing the file on disk is not the same as the running process picking it up; the fix only became live once the process was restarted (this one, at 13:02:12 KST). General lesson: (a) when you fix a stale constant/default, check whether a long-running process cached it at import/startup time, and if so, restart is part of the fix, not optional; (b) don't assume an env-var override is present just because the code supports one — check the live process's actual environment; (c) an index-refresh endpoint invoked without an explicit path argument doesn't do a wholesale corpus replace, it runs a diff (`detect_changes`) then updates the graph, full-text, and embedding indexes — so describe its blast radius as "can produce broad incorrect add/update/delete decisions if it's working off a stale source," not "wipes and rebuilds everything" — keep such severity claims relative and sourced, not absolute.

## 4. Search-result consumption contract (axis 7 — adopted 2026-07-29, operator-approved 2026-07-29)

> Why: retrieval quality improving does not automatically move answer quality by the same margin — this is the retrieval-generation gap, and it's been measured directly, not assumed. Sources are kept clearly separated below (a prior draft of this note, corrected 2026-08-02, collapsed an internal measurement and an external one into a single parenthetical and mislabeled the internal one as "external" — a caution about not letting one citation's label bleed into the next; the reverse case of [source-fact](source-fact.md) §7-2's principle that a value gets discarded per-label, not globally):
> - **Our own measurement** — on the LongMemEval benchmark, 500 questions (dated 2026-07-17): **recall@10 was 0.966 while QA (answer) accuracy was only 0.61**, and **86% of the wrong answers traced to the reader/synthesis step, not to retrieval**. Conclusion: our bottleneck is *reading*, not *finding*. The same benchmark showed an advantage over a plain BM25 baseline (recall@1 0.845 vs. 0.783 · QA 0.610 vs. 0.538). ⚠️ **Measurement-path caveat (correction applied 2026-08-03, operator-approved)**: these numbers came from an adapter's independent approximate re-implementation (dense retrieval with a MiniLM-L12-v2 embedder + bge-reranker-base reranker; graph/entity channels not applicable to this corpus), not from the live production search endpoint — the live embedder is bge-m3, which differs from the approximation. The original write-up had this caveat and it got dropped somewhere in a later citation. Cite these figures only as "approximate dense+rerank reimplementation" results, never as "live system" results. The downstream conclusions (bottleneck = reading; beats BM25) still hold under the approximate conditions, so they stand.
> - **External benchmark** — STaRK-Prime found that even when the correct passage *was* retrieved, it went unused in the final answer **42.6%** of the time, and when placed in the **70-100%** position of a long prompt, usage dropped to **0%** — from a single benchmark/model condition, do not generalize this as a fixed universal threshold.
> - **Our own 24-question benchmark** — the lever that matters is ranking position, not raw candidate count.
>
> Separately from tuning the search tool itself (§1-3), this is the contract for the **consumption layer** — how you read, place, and cite what search hands back.

- **C1 — read the top 3 results, actually**: applies only when you're about to turn search results into a **factual claim, judgment, or deliverable** — open and read the top 3 results' actual content. Do not make a factual/absence/causal judgment from titles or snippets alone. Simple reference lookups or exploratory mid-task searches are exempt from this. If all three just repeat the same point, keep opening results (within the normal fallback chain) until a genuinely different kind of evidence shows up. Cite only documents you actually read.
- **C2 — evidence goes up front**: in follow-up prompts or delegation messages, put the 3 pieces of evidence a conclusion actually depends on at the top, each as `document — one-line evidence — one-line relationship`; secondary material goes after. Do not paste the same evidence into the body, an appendix, and a summary redundantly. (The specific hit-rate-by-position numbers above are from one dataset/model condition — don't treat them as a fixed universal cutoff.)
- **C3 — expanding `top_k` is for absence-verification only**: do not expand top_k to try to improve result quality (measured on the 24-question benchmark: widening the candidate pool pushed out the correct existing result and made things worse). Only expand it when the top results alone can't confirm absence, and label anything found that way as "boundary check," kept separate from your primary evidence.
- **C4 — handing off 3+ documents needs a one-line relationship summary**: when passing 3 or more documents to another bot or a follow-up prompt, add a one-line relationship map (e.g., `A = root-cause measurement · B = our own reproduction · C = the operating rule`). Do not serialize the entire graph's nodes and edges.
