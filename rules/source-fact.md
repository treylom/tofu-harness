# Rule: SOURCE FACT — Verification Discipline

Trigger: about to assert a vault/repo fact or a proper noun, or a system state; right before declaring something "empty / absent / present"; before acknowledging a subordinate agent's report.

## 1. Sourcing obligation (hard rule — corrected 2026-05-21: the earlier mandatory label-format requirement was dropped, but the sourcing/no-speculation obligation itself stays)
- **Every claim needs a cited source** (file:line / URL / quoted command output). **Speculation and hallucination are forbidden.** No source → no assertion.
- The label format (SOURCE FACT / DERIVED INFERENCE / UNCERTAINTY / DELEGATED TASK) is **no longer mandatory** — write a plain, compressed report instead. But keep the discipline of separating the 4 roles (fact / judgment / uncertainty / delegated task) in your own head, so you don't conflate them.
- Regression case: on 2026-05-21 an agent forced the operator's spec phrase ("do it the way that other agent does it") through the 4-way label scheme and produced a wrong inference — a regression back into over-formalizing something the operator had explicitly said to drop ("the whole point was to get rid of that"). This §1 is the corrected baseline after that correction.
- **Attach an `origin` provenance tag when citing a measurement (added 2026-08-03, by 3-way agreement among reviewing agents, as autonomous action item ①** (internal failure-taxonomy code) **from an audit-and-RAG review meeting)**: when you quote a number or an empirical measurement, tag its **provenance**: `origin = internal_measurement (we measured it ourselves) | external_primary (external primary source) | external_secondary (external secondary source)`. The 4-way split above (fact/judgment/uncertainty/delegated-task) is the **role** axis and is orthogonal to this — do not promote `origin` into a 5th role (an external primary source can still be a "fact," and our own measurement can still be "uncertain"). Why: on 2026-08-02 an internally-run measurement (LongMemEval) got mis-attributed in the rules as "(external: …)," and every downstream agent read our own scorecard as someone else's benchmark. This field exists to structurally block that class of mistake. Case-scoped; apply differently as situations warrant; the operator's final call takes precedence ([skill-process](skill-process.md) §6).

## 2. Blocking the single-grep trap
- Do not stop at one grep when applying a SOURCE FACT label. Required: grep across your shared memory store **and** the full topic hub folder, plus proper-noun cross-validation against anything recognized via OCR. Before declaring a folder "empty," search the whole folder.
- **Don't trust a token-optimizer proxy's filtered `ls` output as ground truth**: a token-optimizing shell wrapper repeatedly reported non-empty directories as `"(empty)/count:1"` (2026-05-16, e.g. a skills directory, a Codex cache directory). Re-measure facts with `find` (which bypasses the proxy).
- **Debugging, forensics, and PII checks = a dedicated proxy-free pass (2026-05-16, operator directive)**: a token-optimizer proxy (▶ Fill in: name/path of your setup's token-optimizing shell wrapper, if you run one) can flatten `ls`/`grep`/`stat` output into false-empties, blanked sizes, and mangled matches. For bug debugging, system forensics, and secret/PII scans, bypass the proxy as fits the situation — run the raw/unfiltered form of the command, or use a tool outside your normal shell wrapper. **A subagent's grep runs through the same proxy hook** — don't take a subagent's "CLEAN" report on faith; re-verify yourself with the proxy bypassed (cross-reference: subordinate-report verification discipline, §3 below). **Never bundle a PII check with other work — give it its own proxy-free pass** (empirical incident, 2026-05-16: a subagent reported "CLEAN" through the proxy; a bypassed re-check turned up numerous exposed absolute paths and real names).
- **Proxy-free enforcement expanded (2026-05-24, cross-tool dual-verification pass)**: beyond forensics/debugging/PII above, also require proxy-free (raw/unfiltered) execution for: **(a)** asserting CSV/log row counts or contents via `cat` or a proxy's filtered `read` (the proxy can drop rows or summarize, producing wrong counts or false absence), **(b)** `git status`/`git diff` (the proxy can synthesize a generic "ok" and hide the real diff), **(c)** any assertion of absence/emptiness/existence ("it's not there / it's empty / it exists") — proxy filtering amplifies false-empties. Basis: this session's own repeated proxy `ls "(empty)"` and `git "ok"`-mangling incidents, plus a 2026-05-21 false-empty path misjudgment in an IPC-adjacent investigation.
- **✅ Global bypass hook shipped and verified green (2026-06-10)**: the structural limit above ("if a human forgets, the failure is silent") is now closed by a **global pre-tool hook** (installed on the Bash tool path) that auto-bypasses to raw execution for: all of git / forensics-PII-secret keywords (in any language) / `find`·`stat`·`du`·`wc`·`ls`·`rg`·`grep` / `cat` on `*.csv|log|jsonl|tsv` — everything else still goes through the proxy rewrite. **2026-06-10, 8-case verification**: git, find, ls, grep, and cat-on-csv all bypassed correctly; npm and cargo commands were still proxy-rewritten as expected. The manual carve-outs above are now a **second line of defense** (for when the hook fails open, for non-Bash tool paths, and for subagent environments where the hook may not apply).

    - ✅ **Cheapest fix = `command grep` or `/usr/bin/grep`** — works regardless of path, repo size, or spelling. Use one of these for any counting or absence judgment (a dedicated Grep *tool*, if one exists in your harness, is a separate layer and out of scope here).

Because the underlying corpus changes while you're measuring it, always record `observed_at` (one drift of 4,549 → 4,550 was measured 2 minutes apart).

    - 🔴 **There are two mechanisms, not one — ② (byte-skip via `-I`) is unrelated to gitignore (confirmed 2026-08-01, 14:4x)**: a remaining flagged file (a specific report file inside an agent working-directory tree) was **not** a gitignore issue — `--no-ignore-files` still returned **0**, but `-a` (which disables `-I`) returned **1**. `file` classified it as `Non-ISO extended-ASCII text … NEL line terminators` (despite zero NUL bytes) — i.e., it was misclassified as binary.       - ⇒ **mechanism ① (`--ignore-files`) is rule-based (readable, so predictable); mechanism ② (`-I`) operates on raw file bytes (leaves no trace in any rule).** ② is more dangerous — **a single stray NUL byte (1 byte), or a single invalid UTF-8 byte, is enough to make `-I` drop the entire file** (⚠️ the earlier "NEL / non-UTF8" characterization was imprecise — NEL itself is not the trigger; see below). The earlier theory that the missing content was "the product of a 231-line rule-file combination" is **retracted** — that was the investigator's own hypothesis narrowing the search (once mechanism ① was found, there was no felt need to keep looking for ②; **when you set your own stopping condition inside your own hypothesis, you stop seeing the mechanisms outside it**).

If you must use the shim, use **both** `-a` and `--no-ignore-files` together — either alone is only a partial fix (a closed-loop measurement: mechanism ① alone accounts for a loss of 84, mechanism ② alone for a loss of 2, and turning both off recovers the true value of 4,550).
      - 🔴 **The right detector is an `-a` A/B test, not `file`** (a case that killed the `file`-based fix within one round of testing): for one flagged file, `file` reported plain `Unicode text, UTF-8 text`, yet `-I` still dropped it (**51 NUL bytes**, confirmed independently 3 ways — `od -tx1`, Perl, and Python, all agreeing). For a different flagged file, the count was 0 NUL bytes plus a UTF-8 invalidity at byte offset 3117. **There are two distinct triggers, and `file` catches neither reliably.** Furthermore, **"binary" is a detector's judgment call, not an intrinsic file property** (an independent check found that with the same `-I` flag, a BSD `/usr/bin/grep` still included that same file). ⇒ whenever you cite an `encoding_class`, pair it with `detector_id + revision + options`, and **never treat a single `-I` run as proof of absence**.
      - **Full-corpus rerun** (repo root, `.`, `*.md`, **empty pattern** — i.e. the pattern-independent ceiling count) — ⚠️ **the corpus was changing while this was measured, so `observed_at` is mandatory**: **14:42 KST = 30 affected files** (shim 29,530 / `-a` 29,560) → **14:52 KST = 31 affected files**. Breakdown: **28 files** inside one project's daily verification-log directory (dated 2026-04-11–2026-05-25, with gaps — the earlier count of "29" for this group was **a manual miscount by eye; recount mechanically**), plus **2 named files**, plus **1 newly-affected file at 14:5x** (see the self-catch below). ⚠️ **Of that 65-file log directory, 28 of the 65 are invisible to grep** (visible: 37 — the earlier claim that "the whole folder is invisible" was **an overstatement and is withdrawn**). This isn't a wrong-value problem — specific dated logs within a time series become invisible, so what you see is **gaps in a date range**, not corruption. The `*.py` axis showed **0** loss (this is `.md`-specific).
      - 🔴 **A document that records literal control characters can make itself disappear from search (self-caught live, 2026-08-01, 14:5x)**: a meeting-progress file newly entered the 14:5x affected set. Cause: while documenting this exact measurement pitfall, shell-interpreted notation like `tr -dc '\000'` and `b.count(b'\x00')` got written into the file, and the shell interpretation turned them into **3 literal NUL bytes actually embedded in the file** (at two adjacent lines, 179-180, in both the working copy and the published copy). ⇒ **the note documenting the NUL-byte pitfall disappeared from grep because of a NUL byte.** Fix: when writing control-character literals into docs/logs, either route them through a path that skips shell interpretation, or double-escape them (e.g. `\\000`). **Check meeting/SoT files for embedded NULs once after every append** — a source-of-truth doc becoming unsearchable is worse than a wrong value inside it. ⚠️ **Do not check for this with `grep -c $'\x00'`** (confirmed wrong by a positive/negative-control test, 2026-08-01, 18:02): the shell can't put a literal NUL into argv, so the pattern silently becomes empty, and an empty-pattern grep matches every line — **regardless of whether NUL is present** (it becomes a line-counter, not a detector). The correct check is `python3 -c "import sys;print(open(sys.argv[1],'rb').read().count(bytes([0])))" <file>` (use `bytes([0])` — an earlier `b'\x00'`-style literal died from f-string escaping) or `tr -dc '\000' < <file> | wc -c`. **Any new detection command you introduce or hand off must ship with a positive control** (plant one known NUL and confirm detection) — this is the self-application of "detect when your detector itself has died," internal failure-taxonomy code G8(a).
      - **The precise axis is "which root the search starts from"** (a self-correction — absolute vs. relative vs. repo-root vs. subdirectory all differ): summing per-subdirectory relative searches gave 4,547, vs. 4,464 for a single relative search from `.` — an 83-file gap between two searches that were both nominally "relative." The earlier "depends on cwd" and "absolute-vs-relative" labels were both partial observations of this one underlying axis.
      - ✅ **Mechanism ② trigger fully confirmed = "NUL byte present OR invalid UTF-8" (exhaustive check, 2026-08-01, 14:5x, zero remaining exceptions)**: across all 65 files in that log directory, the split was **perfectly clean** — 37 visible = zero NUL AND valid UTF-8; 28 invisible = **UTF-8-invalid only** (28), NUL-only (0), both (0). Each trigger's proof case: NUL — a file that was UTF-8-**valid** but had 51 NUL bytes; UTF-8-invalid — a file with 0 NUL bytes and an invalidity at offset 3117, matching the pattern of the 28 log files. ⚠️ **`0x85` (NEL) is not the trigger** — it commonly shows up as the continuation byte of a 3-byte character in non-Latin text (e.g. `EA B0 85`), and plenty of visible files contain it too. Don't read `file`'s "NEL line terminators" label as a cause.
      - ⚠️ **The shim only exists in interactive shells — the measurement environment itself is a variable** (a self-caught mistake): the same command run **directly through the coding tool's own Bash execution → 37**, vs. run **via a `zsh -c` subprocess → 65** (the true `/usr/bin/grep` value). ⇒ `grep` inside a script or subprocess does not go through the shim. To measure the shim's own behavior you must run it directly through the tool's own Bash path; conversely, **a list pulled via a script must not be mistaken for a shim-filtered result** (this happened once — a contaminated list produced one wrong rule-conclusion).
      - ⚖️ **Meta-lesson from this whole track**: across 3 consecutive mislabelings (proxy → cwd → absolute-vs-relative), the underlying value was wrong 0 times (the cleanest instance of the "the label dies, not the value" pattern, §7-1).     - **Corpus-size-alone and cwd-alone theories are both rejected; the earlier "suppression-rate curve" idea stays retracted** (neither corpus size nor cwd alone is the real variable). **Working conclusion, unchanged: for counting or absence judgments, use `command grep`.**
    - **Cross-total/sum-matching is a detector, not a corrector** (unchanged from the earlier finding) — a mismatch is only a signal of malfunction; **never adopt either value from a mismatch**, always re-measure via an independent path. Two measurements agreeing after sharing the same suppression is not evidence of correctness (a case where 1,630 = 1,501 + 129 matched internally and was still wrong is the proof).

- **When a tool's output contradicts a file/state you just changed, check the infrastructure hypothesis before anything else (empirical incident, 2026-07-02, pattern #5 of a session review)**: if a file or state you just fixed doesn't show up in a service/tool query, don't retry the same tool or declare "the tool is broken" — probe with an orthogonal method first, across 3 candidate nodes: ① **cache staleness** (re-query with a cache-busting param/header) ② **lag** (async delay — re-check after a pause) ③ **an intermediary/bridge layer** (check the origin directly; cross-check via a separate fetch path). ## 3. Verifying subordinate-agent reports (hard rule)
- Before acknowledging a report, an orchestrating agent must: self-identify the reporting agent, verify against actual filesystem state, and cross-check via message-fetch. Always assume the possibility of multiple concurrent instances under the same bot account.

## 5. Self-diagnosing regressions
- Accumulating feedback notes doesn't prevent repeat violations — "knowing the rule" is not the same as "the rule being enforced." ## 6. Answer-time verification gate (operator-approved 2026-07-18)
Trigger: whenever an utterance — especially a conversational quick-answer or a DM reply — is about to carry ⓐ **a new factual claim or number**, ⓑ **a causal diagnosis** ("...because...") or ⓒ **a prescription/suggestion** ("...just do..."). Routine status updates, progress reports, and opinions are exempt. (Basis for this gate: in a review of prior violations across all agents, 10 of 14 cases happened at exactly this quick-answer moment — the earlier gate only covered task time, not answer time.)
1. **Minimum pre-utterance check = "1 canonical source + 1 counter-check"**: open the canonical source on the topic once (the relevant doc's decision/disposition section, a progress log, a bug report, or a prior correction in this conversation), and run one search for a counter-argument to your own reading ("is this already on record? is there a contradicting explanation?"). **These 2 checks are sufficient** — repeating beyond that is over-verification (consistent with the self-convergence limit in [code-quality](code-quality.md) §7).
2. **If unverified, there are 2 options**: ① reply first with **"let me confirm and get back to you in N minutes"** (the operator has explicitly endorsed this as normal practice — a slow correct answer beats a fast wrong one) ② answer, but **flag it explicitly as unconfirmed** ("provisional, pending source-check"). Asserting or prescribing while unverified is not allowed.
3. **Utterance format = 1 line of grounding**: attach one line to any factual claim/diagnosis/prescription — either "grounds: already on record at `<canonical file/§>`" or "new — <what you just measured>." (This structurally prevents mistaking an already-recorded fact for a fresh discovery.)
4. **Adjacent-axis coverage**: before declaring a just-attempted action a failure, check for evidence it already succeeded (prevents redundant retries — this class of regression has caused duplicate message-sends before); before amplifying something another agent or person said, check the original source once; before declaring a failure, search past records for a prior success first.
5. **Confirming who/what a task actually targets (added from a 2026-07-22 harness retrospective, item E3b, conditional gate)**: if a task's target reference **could map to more than one real system entity** (e.g. same-named repos, multiple deployed layers) **and** the action is a **mutation or a public-facing action**, confirm before starting: state `TARGET: <resolved entity path/repo>` explicitly (either by asking the requester or by empirical cross-check, with your interpretation stated out loud). Does not apply when there's a single unambiguous entity or the action is read-only (don't over-apply this). Regression basis: on 2026-07-21 a plugin's name was misread across 3 stages (an installer path → an in-plugin skill → a public 12-item marketplace listing) before being corrected 2 times by the operator.
- If you catch this violation in yourself or another agent, log it once to shared memory (to track recurrence). Gray areas ("is this actually a factual claim?") default to applying the gate. Case-scoped to one incident (2026-07-18, an agent's mistaken diagnosis of a model called gpt-oss); situational re-judgment applies; the operator's final call takes precedence ([skill-process](skill-process.md) §6).

## 7. Labeling discipline — what usually dies is the name, not the value (harness-audit finding, 2026-07-25)
> 🔴 **Correction (2026-07-26, 05:2x)** — the earlier title ("values never die, only names die") and the earlier claim of "0 value errors across the full set" are both **retracted**. The original basis was **each of 3 reviewing agents' own self-compiled lists** — not an exhaustive census (no shared merge criteria existed beforehand, so "exhaustive" was never actually verified), and "0 value errors" was **also false** — 3 recorded counter-examples exist: ① a claimed "40-minute interval" measured at **27 min 51 sec**, ② a one-digit typo in a bot user-ID, ③ a `wc -m` reading of 15,261 that was actually a **byte** count (the true character count was 8,638, under a `LC_CTYPE=C` locale). What survives is only *a same-day sample's tendency for labels to fail more often* — **not a law**. However, within one reviewer's list of 12 items, the finding "0 of 12 were value errors" **still holds inside that population** — what's retracted is only the leap from *0/12 in that sample* to *a general law* (**a refutation's reach only extends as far as the generalization; the scoped source-population measurement survives**). Rules 1-3 below are unchanged.
1. **Claims of separateness, completeness, currency, or a ceiling need an explicit axis**: axis-free words like "separate," "exhaustive," "current," or "ceiling" can cover a safe axis and a risky axis with one word (example: an isolation setup where identity was separated but the backend was still shared). When you assert one of these, state **which specific axis** is separated/complete/current.
2. **Discard at the label level, not the value level**: don't manage a discard-list of value strings — what usually dies is the name attached to it (example: a "786 items = 7 days" label died while the number 786 survived). In prose, a value's label is often implicit (position stands in for the label), so retiring it means: ① make the implicit label explicit first (state as-of date, ownership, and status) ② then retire that label. Where a value sits in a position a parser reads (a single fixed role), removing the value itself is correct there — that's a per-position judgment call.
3. **"Unknown" also splits three ways**: unresolved (measured, but no rule derived yet) ≠ unmeasured (never measured) ≠ out of scope (can't be measured with your current tools) — tag which one it is, so the next person knows where to pick up.
4. **Citation contract = 6 fields** (added 2026-07-26, expanded the same day): `target_path + metric + value + observed_at + content_revision (mtime/SHA) + environment (locale · what a name resolved to · cwd, etc.)` — none of these substitute for another. **A citation of a measured value must also include `+ origin`** (§1's provenance tag — internal_measurement/external_primary/external_secondary; added 2026-08-03 after a review found §1 and this field were disconnected). 🔴 **The `environment` field must state `resolved_executable`** (added 2026-08-01, based on a proposal and an empirical confirmation): the same command *string* can resolve to different things depending on what that name is bound to — proven by `grep` being zsh-function-bound to a bundled matcher binary, producing 0 vs. 14,374 for the identical command (§2 above). **For any non-trivial count or absence judgment, resolve the target once with `type -a <cmd>` or `which <cmd>`,** and record that alongside the value. ⚠️ This conclusion is scoped to **one specific combination** (a coding-tool zsh shim × a repo's allowlist-style `.gitignore`) — **do not generalize it to other shells/harnesses** without checking each independently. ⚠️ **The older 5-field contract** (no `target_path`, phrased as "source revision") **is historical — do not use it for new citations** (the 6-field contract was finalized in a written correspondence 2026-07-26; propagated 14:1x). When **combining multiple sources** into one value, add `+ source + aggregation_rule`; for **history/attribution**, add `+ provenance_role + introducing_commit + author` (additive to the single-measurement contract, not a substitute — mixing them into the same field causes misreads). In particular, **never run an unqualified `wc -m`** (character vs. byte count depends on locale): for characters use `LC_ALL=C.UTF-8 wc -m` or a language's own `len()`; for bytes use `wc -c`.
5. **A correction must be traced through every place that cites the value, including derived numbers**: fixing only the measurement line leaves any summary/verdict lines that cited it, and any derived calculations, stale (a real case: the re-measurement was logged correctly, but 4 summary lines in the same document kept citing the old value). **Polarity flips (an inverted negation) are a separate failure mode** — the value and the name both stay intact, so **literal/file-integrity-style checks alone (grep, checksums, character counts) cannot detect whether a restatement preserved the original's polarity** (⚠️ this is not "undetectable by any check" — **a polarity check anchored to the original message ID does catch it**). So: citations should be **verbatim, with a source message ID**; verdicts should use a **polarity check**.
- Case-scoped to one incident (2026-07-25–26 — most labels died across 3 reviewing agents' individually-compiled lists; ⚠️ not "all" of them); situational re-judgment applies; operator's final call takes precedence ([skill-process](skill-process.md) §6).

## 8. Checker discipline — pass messages, signal placement, transcription (internal code G4 — operator go-ahead, 2026-08-05)
When building or consuming the output of a checker (a health check, a gate, a counter, a verification script):
1. **A passing message must carry 2 lines**: "the question this check answers" + "what it compared that answer against" — a full-corpus scan only earns a *slot*, the verdict still comes from the canonical source (confirmed by a case where a full-corpus check was wrong 2 out of 3 times). Don't use a raw-count threshold ("N or more = ok") — use a named expected-set enumeration plus a canonical-source comparison.
2. **Signal placement**: don't mix warning/incomplete signals into the body of a success message — put them on a separate line, under a separate label, or escalate the exit status. **Never print a count of 0 as a pass** (`injected 0` / `matched 0` are failures wearing a success sentence's face) — **a plausible-looking non-zero number is also suspect** (looking like an answer ≠ having actually measured one). The 3 shapes of "failure printed in success format": a warning folded into the body, a 0/no value wearing a value's face, and an exit code that disagrees with the body text (a wrapper's exit code must reflect the underlying failure count).
3. **Transcription reconciliation**: any number you transcribe from a source must be **column-summed against the original** — transcription without a check is duplication without verification (a real case double-counted on both the submitter's and the aggregator's side). When using a transcript itself as your ruler, explicitly design out **self-reference contamination** in your control group (the act of measuring gets recorded into the thing being measured).
4. A checker's own survival requires built-in positive and negative controls, and **the type of bait must match the type of defect** (all 3 checker deaths recorded in one day were caught by a positive control).
- Case-scoped (a 2026-08-05 S1 census, 40 items, plus an S4 empirical follow-up pass); situational re-judgment applies; operator's final call takes precedence ([skill-process](skill-process.md) §6).
