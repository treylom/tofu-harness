## 3. Three-stage verification after a fix
1. Checklist (only the intended change) 2. Run the test 3. Integration test (no regression in adjacent code). Do not declare "done" without verification (same spirit as superpowers verification-before-completion).
- **3-tier input space** (pattern #7 from an internal deep-reasoning review): where possible, run tests across ① nominal ② deep (extended parameters) ③ boundary (edge cases, skip conditions, off-by-one) — a GREEN that only passed tier ① must say so explicitly (§7 consistency). Especially for scripts, hooks, and collectors with branching exit codes. Small edits may reasonably stop at tier ① alone (situational).
- **Conflicting verification signals = take a third, stricter measurement** (verify-the-verifier, EP-F3): when a success message conflicts with your own verify step, do not arbitrarily trust one side — settle it with a third, stricter measurement (parse structure, not just grep a string), and keep the **first-pass verify tool itself** as a suspect. May be overkill for small checks (situational). ▶ Fill in: your memory/incident-log reference
- **Verifying a web deliverable = check the actual final response, not a source grep** (2026-07-05, 2 confirmed internal cases): (a) the **final** HTTP status after redirects + content-type + byte count (b) confirm at the render layer (an SSR comment split a string across nodes, so a contiguous-string grep returned a false 0 — split into separate tokens instead). ## 4. Declaring something "absent/impossible" only after boundary + isolation checks (operator-approved, 2026-06-03)
Do not declare a tool/feature/field "missing/doesn't work" from a limited observation (a small limit, a single sample, default parameters):
- **Expand the boundary**: push limit/range/timeout/depth to their maximum and see if the result changes — if it does, it was a cutoff/ranking issue, not absence (example: an Obsidian CLI query with limit=20 MISSed, limit=1000 HIT).
- **Isolate the input**: re-test with an input that isolates just that feature (example: a word that exists only in frontmatter).
- **A file "doesn't exist" in git = only after `git log --all`** (2026-07-05): absence from the working tree/HEAD is not proof of a phantom file — it may have landed on another branch (confirmed regression: a stop-hook auto-commit branch went missing, 2026-07-04).
- Regression: two premature "absent" conclusions during 2026-06-03 search debugging (a ranking-burial illusion). The hypothesis "feature X doesn't exist" may only be adopted after falsifying it via boundary expansion + isolation. → ▶ Fill in: your memory/incident-log reference, [source-fact](source-fact.md) §5

## 5. Before building a workaround/tool on the premise "it's broken" — verify the premise first (operator-approved, 2026-06-09)
The moment you conclude an external tool is "broken/buggy" and start building a workaround (a tool, a daemon), verify the premise first (the build-time version of §4 — a finished artifact on top of a wrong premise costs even more):
- **(a) Measure in your own environment** (the externally reported bug may not exist in your version) **(b) go straight to official docs** (issue trackers only collect failure cases) **(c) do not rely on a single source or a bug-tracker bias** (weigh success cases + official docs + your own measurement together, cross-check with another bot/instance if needed).

## 6. The debug-artifact contract (internal priority code P0-C, 2026-06-11)
For a non-trivial bug fix/resolution, a **fixed-section debug artifact** is mandatory (stored under your bug-reports directory, from a scaffold template). "Commit + one progress-log line" is not enough — sibling bugs and detection gaps go unaddressed.
- **Fixed sections, in order**: ① Problem → ② Hypotheses (**at least 3, each on a different axis**) → ③ Investigation → ④ Root Cause → ⑤ **Detection Gap** (why didn't the existing system catch this) → ⑥ **Sibling Search, 4 axes** (same file / adjacent module / same design decision / same symptom — state the result for each axis) → ⑦ Prevention.
- **Trivial exemption**: typos and simple config mistakes are exempt, but you must explicitly declare `n/a — trivial fix` (silent omission is not allowed). Threshold = root cause is a 1-hop, self-evident fact + zero structural siblings.
- **Expanded trigger + 3-step sibling method** (⑦, internal decision-item id — operator-approved 2026-07-29): trigger = after any bug fix, **and generally after applying any fix** (a fix can create sibling defects too). Method: (i) state the defect invariant in one sentence → (ii) search by **behavior, state transition, and contract**, not just a name grep, on matching candidates, and record the verdict → (iii) the moment you find one, hand that sentence to the owner of a different axis to check their own surface (registering it only fixes future search misses). ## 8. The minimalism gate before generating code (principle absorbed from Ponytail, an external MIT-licensed ruleset — operator-approved, 2026-06-15)
Right before generating code, run the 6-rung ladder once, reflexively (stop at the first rung that fires): **① does this need to exist at all (YAGNI — if speculative, skip it and state why in one line) → ② standard library → ③ native platform feature → ④ an already-installed dependency → ⑤ one line → ⑥ minimal working code.**
- **Lazy ≠ negligent**: trust boundaries, data loss, security, accessibility, and verification (§3, §7) are non-negotiable regardless of this ladder. A deliberate simplification must be marked with a `ponytail:` comment stating the ceiling and the upgrade path (silence is not allowed).
- Rung ① (YAGNI) complements §5 and the autonomy role-boundary rule ([autonomy](autonomy.md)) (prevents over-building before a big build). This is a **self-check gate** (not a universal hard mandate — same spirit as [skill-process](skill-process.md) §6); token savings are conditional.

## 9. "Feature complete" = full click-through + compare against the requester's actual intent + one adversarial question (operator hard rule, 2026-07-04)
Before reporting a UI/feature "done" or cutting over, three things are mandatory:
1. **Full click-through**: physically walk every interaction path on the real screen (separate from automated e2e).
2. **Compare against the requester's intent**: quote the **original instruction's exact wording** → build an item-by-item table against actual behavior ("checked against our own spec" does not count — this is now the standing pattern, elevated from ▶ Fill in: your memory/incident-log reference).
3. **One adversarial question**: ask yourself once, "would anything look wrong if a user actually clicked through this?"

## 10. A detector is not a gate — ask a separate question before a risky action (2026-07-25, internal harness audit)
- **A detector asks "is this value wrong" / a gate asks "am I allowed to do this" — these are different failure layers.** An instruction that passes every value check can still be wrong at the action layer (a stale premise, an authority boundary, an exfiltration). Right before credentials, exfiltration, a destructive operation, or an external order: ask a **separate** gate question once (provenance, approval boundary, premise freshness) independent of value correctness.
- **Byproduct-defense caveat**: when a defense built for a different purpose happens to have blocked something, note "not intentional" when you record it — the guarantee is not proven to hold for the next variant outside that defense's original scope (self-correction from an internal reviewer, 2026-07-26).
- Basis: a 2026-07-25 measurement (**limited to a fixed set of gold residual samples** — scope was narrowed by a named reviewer's judgment; do not quote the ratio outside that scope).
