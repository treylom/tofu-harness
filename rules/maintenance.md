# Rule: Harness Periodic Review Cadence (Keeping Pace with Model Evolution)

Triggers: right after a model's major release · 90 days (one quarter) since the last review · the moment you notice tool docs or rule text drifting out of sync with actual state.

> **Why**: "Claude Code at Scale" blog, pattern 2 — *"Re-review your CLAUDE.md every 3-6 months as models evolve. Stale rules written for a weaker model's limits will constrain a stronger one; tool docs that no longer match reality quietly degrade harness performance."* Our rules get updated all the time on an ad-hoc basis, but there was no *periodic* alignment check. One incident that motivated this rule: a rule file claimed "no language server in use" and "code-indexing tool: 17486 symbols indexed" — while the actual state was a live TypeScript language server plus an indexing tool that had never actually indexed anything. Ad-hoc updates never caught this; the missing piece was a periodic check. (▶ Fill in: link to your own write-up of this kind of incident, if you keep one.)

## 1. Checklist (Review Items)
1. **Tool docs ↔ actual state**: do the tools your rule files/CLAUDE.md mention (language servers, code-indexing tools, MCP servers, hooks, plugins) match what's actually installed, enabled, and working — measure it directly (e.g. your plugin-manager's enabled-plugins list, `npx <tool> status`, `claude mcp list`), don't take the doc's word for it (rtk-free measurement; see [source-fact](source-fact.md) §2).
2. **Old rules ↔ new model capability**: do rules written to compensate for an older/weaker model (assuming a small context window, over-aggressive task-splitting instructions, excessive confirm-before-acting) now constrain a model that doesn't need that compensation anymore?
3. **Rules INDEX ↔ rule files consistency**: does your INDEX trigger table map 1:1 to the actual `.claude/rules/*.md` files — any dead links, any rules missing from the table?
4. **Memory staleness**: do your shared-memory index entries still match the actual files/state they point to (tool paths and bot rosters especially — see your deployment's memory rule §3)?
5. **Per-bot live-model cross-check (item 12 in one internal periodic-review round — approved 2026-07-29, axis 1 and axis 3 of that item already executed)**: does the model your launch command names, and the model your working-directory docs claim, actually match the model that's live in the running session?
   - ⚠️ **There are two launch surfaces, not one** — your shell profile (the actual runtime source of truth for how a bot is launched) and any mirror script that launches the same bot a second way (e.g. a `launch-bot.sh`-style wrapper). One internal audit found three bots' recorded model values had drifted apart from each other because only one of the two surfaces had been updated — and the mirror's own comment claimed "identical to the shell-profile function," so the comment itself failed to catch it. ⇒ **cross-check both surfaces by machine comparison, not by eye** — a prior pass fixed the two bots that had been flagged and missed that the third had been silently repointed to a value that merely *looked* like an explicit model ID.
   - A model alias is a snapshot — it silently rides along on a version bump without anyone noticing (real example: an alias like `opus[1m]` moved to point at a newer model release and three bots didn't register the change). The fix is to record an explicit, fully-qualified model ID rather than a movable alias. The tradeoff: you give up automatic pickup of upgrades, and take on stale-value debt instead — and the only two paths back to a correct value are (1) an explicit operator instruction, or (2) this periodic review. If neither ever runs, you're worse off than you were with an alias.
   - When you record a model, keep the model ID and any context-window flag (e.g. `[1m]`) as two separate fields — the flag is not part of the ID. Don't copy the value into derived surfaces (a working-directory CLAUDE.md, etc.) — point at the source of truth plus an "as of" date instead; only the persona/identity file itself should carry the live value (so it's strongly self-injected).
   - To confirm which model actually ran a session, check the transcript's `message.model` field directly — that's the ground truth.
   - **Choosing the model is the operator's call** — this checklist item is about recording and observing it accurately, not about picking it. (▶ Fill in: link to your own design note on bot-startup protocol, if you keep one.) Treat this as case-by-case guidance, re-judge per situation, and defer to the operator's final call.

6. **Skill/subagent scope-name collisions (approved 2026-08-02, prompted by an external conversation)**: if the same name exists at both the personal scope (e.g. `~/.claude/`) and the project scope (e.g. `.claude/`), **the two resolve with opposite priority** — per official docs, skills resolve `enterprise > personal > project` (personal wins), while subagents resolve `managed > CLI > project > user > plugin` (project wins).
   - ⚠️ **The dangerous direction is skills**: most of our rule-enforcing skills live at project scope, but since **personal wins**, a same-named skill dropped into the personal folder will **silently disable the project rule with no warning or error**. Subagents have the opposite priority (project wins), so they don't carry this risk.
   - Check with a scope-collision-check script (▶ Fill in: your own script path, e.g. `your-scope-collision-check.sh <repo>`) — **build in a positive control**: if either scope's total count comes back 0, that's not "no collisions," that's a **RED — the checker itself is broken** (guards against a silently-empty check). Use a **3-way exit code split**: `0` = clean, `1` = collision found, `2` = checker itself broken. (An earlier version of this check collapsed "found a collision" down to the same `0` as clean, so hooks/CI couldn't tell them apart — the checker found the defect and still signaled "pass." All three paths were verified empirically: 0 on a clean repo, 1 after deliberately planting one collision, 2 when the total-count denominator itself came back 0; then reverted.) ⚠️ **An exit code is a signal, not a policy** — whether it blocks anything is the caller's decision; don't wire a hook to read `1` as an automatic commit-block without deciding that on purpose.
   - One measurement (dated): skills — 16 at personal scope / 59 at project scope; subagents — 7 at user scope / 14 at project scope; **0 collisions** found. That 0 was confirmed by planting one collision and watching it get caught (then reverting) — a genuine negative control, not an assumption. Note that a 0 like this can also just mean "no one happened to reuse a name yet," which is luck, not a guarantee — don't read absence-by-luck as absence-by-design.
   - 🆕 **Nested same-name collisions follow a different rule again** (verified against a synthetic fixture, two conditions compared): within a single scope, if a subdirectory has a skill with the same bare name as one at the root, (i) the bare (unqualified) name **always** resolves to the root/unscoped skill, (ii) the subdirectory variant is reachable **only** by its exact qualified name (e.g. `sub/pkg:name`), and (iii) that qualified name only shows up in the skill list **after** something has read a file in that subdirectory at least once.
     - ⇒ this isn't a priority problem, it's a **namespace-reachability** problem — there's no way to invoke the nested variant by its short name at all.
     - 🔴 **Operational implication**: if a bot never touches its own working-directory files, its own skill may never appear in its list — "that skill doesn't exist" may be *non-exposure*, not *absence*.
     - To reproduce: place a same-named skill fixture in a subdirectory, compare the skill list and short-name-invoke result before and after touching a file in that subdirectory (before = qualified name absent, root wins alone; after = qualified name appears, and the short name still resolves to root).
     - ⚠️ Any in-tool guidance suggesting a workaround for this depends on the model actually following it — don't count the existence of that guidance as a real mitigation on its own.
   - A more durable fix (not yet rolled out, pending a scope review) is giving important rule-enforcing skills a **plugin namespace** (`plugin:skill` — documented as immune to cross-layer collision; e.g. `km:`, `ouroboros:`-style prefixes). Treat as case-by-case, re-judge per situation, operator's final call (see [skill-process](skill-process.md) §6).
   - 📦 **When you port this checklist item into a downstream rule bundle, don't merge it into one file** — the *prevention* half (check for a same name before creating a new skill) and the *detection* half (this periodic sweep) fire at opposite times (creation time vs. quarterly), so putting only one of them in your bundle leaves a gap either right up until the next review, or for anything created before you started checking.

## 2. Cadence · Ownership · Log
- **Cadence**: once after every model major release, plus once per quarter (90 days from the last review date).
- **Who runs it**: the orchestrator role owns running the check. **Registering it as a recurring cron job is delegated to whichever role/bot owns your scheduling domain** (see [orchestration](orchestration.md) §3 and [meeting-protocol](meeting-protocol.md) §5 for how that handoff is coordinated).
- **Review log**: record the review date and outcome (clean, or N drift items corrected) in one line, either at the bottom of this rule file or in shared memory.

## 3. When Drift Is Found
- Fix the affected document immediately (CLAUDE.md, a rule file, memory, a note) and run the 3-step verification described in [code-quality](code-quality.md) §3. Don't let a "this is stale" claim sit unfixed and get repeated as fact — see [source-fact](source-fact.md).
