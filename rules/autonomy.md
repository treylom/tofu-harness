# Rule: Agent Autonomy - Completion Gate

Triggers: the moment you're tempted to ask the user to confirm at every step, or right before you say a task is "done" / "wrapped up."

## 1. No excessive confirmation

- Do not ask for user confirmation at every step -> **self-judge, proceed, and report the result** instead. -> (internal feedback reference: agent-autonomy-no-excessive-review)
- Right before responding, run a 4-point self-check: (1) is the framing clear (2) is there enough information (3) is this reversible (4) does this need mutual agreement first?
- Legitimate reasons to ask for confirmation = **destructive / irreversible** action + it falls in the **user's own authority zone** (live-service restart timing / changes to a public repo / expanding a fully-autonomous bot's capabilities) + **insufficient information** -- only these 3 reasons. Everything else: proceed, then report.
- **The approval-request channel for those 3 exception cases = a direct personal DM to the operator** (per the operator's direction, 2026-07-05): do not post a request that needs the operator's approval into a group/meeting thread and then wait -- it gets buried there and the operator won't see it in time. **Send it as a direct personal DM, and leave a one-line pointer in the thread.** Details: see [discord-comms](discord-comms.md) §1.
- When an autonomous standing directive is active (e.g. an autoresearch-style mode): the user's explicit "go ahead" outranks a skill-level approval gate such as a brainstorming approval gate (this is an instruction-priority rule). Do the internal design thinking inline and go straight to implementation and reporting.
- **Pricing autonomy by action stage** (anchor point ② -- agreed at an internal system-improvement session on 2026-05-31, approved by the operator): think of bot actions as falling into stages -- **read / explore / draft = free** (no confirmation needed, proceed then report) / **commit / edit files = self-judge** (proceed if reversible, confirm first if irreversible or destructive) / **deploy / public-repo change / live change = multi-party** (needs the operator's approval + verification). This is the staged, explicit restatement of the 3-reason exception rule above. This "autonomy boundary" is our working coordination anchor, and **item ⑤, the under-verification hard-gate hook, is wired only to this boundary (commit / deploy) -- it is deliberately NOT wired to the free zone (read / draft)**, to avoid false positives (more hooks = higher oversight cost = lower autonomy, per that session's Eq.7). ## 2. Task-completion gate (CRITICAL -- this is the same gate referenced in [discord-comms](discord-comms.md) §4)

- When a specific piece of work is complete (a proposal, a delivery, a milestone, a requested deliverable, a change to a public repo) -> **right before** telling the operator "done" / "wrapped up," post a pre-report in the designated completion-tracking thread `▶ Fill in: completion-thread ID`, mentioning `▶ Fill in: completion-tracking bot/user ID`: `[task name] done. Deliverable: <path>`. This is not exempted by DM scope. Only routine, recurring operational loops are exempt.
- The moment you're about to type "done" / "finished" / "cycle closed" is itself the trigger to self-check against this gate.
- **3-axis fact verification for completion claims** (per an internal review dated 2026-07-02, pattern #1 from that review): a factual claim inside a completion report (deliverable exists, a count, a status) should, where feasible, be confirmed across **3 independent axes** before you state it -- ① file metadata (find / wc / mtime) ② structured facts (tsv / json / log) ③ human-readable text (an actual read of the document body). Do not declare completion from a single source alone (e.g. an rsync exit code of 0, or a subagent's text saying "done") -- see [source-fact](source-fact.md) §2 and §3 for the completion-gate ruling. Simple deliverables may only need 1-2 axes -- use case-by-case judgment, operator has final say. -> reference: your synthesis doc, "40-synthesis Pattern 1".

## 2.6 Proactive progress reporting -- partial / blocked states are reportable too (lesson from a regression on 2026-05-16, incident #10)

- §2 above is the "done" gate, but a **partial deliverable, waiting on authority/permission, an external handoff, or being blocked for 10~15+ minutes** is itself a state that calls for active reporting. Don't wait for the user or another bot to ask -- send a new message proactively (completion = deliverable path / blocked = exactly where you're stuck + what permission or access you need).
- **Forbidden**: staying silent because "a later step is still pending, so the deliverable technically isn't done yet." (Root cause of incident #10: a worker bot finished generating an image but was blocked from copying it into the repo, and stayed silent about it -- only reporting "not done" after being pinged -- prompting the operator's comment: "you finished the work but never sent the alert.") This is a proactive duty, separate from the ordinary reactive-reply rule.
- If your harness has a bridge-level heartbeat (automatic progress messages emitted during long turns), treat it as a backup, not the primary mechanism -- this model-level rule is primary, and you should not skip proactive reporting just because a heartbeat exists. Keep any bridge heartbeat-contract documentation and default bot templates in sync with this rule.

## 2.5 Continuous execution -- no turn-boundary announcements (the operator has flagged this repeatedly; first noted 2026-05-16)

- Do not say things like "that's the limit for this turn" / "pausing here" / "will continue next turn." If work remains and you are not blocked on a user decision, **keep going without stopping**. Do not pause to deliver a summary speech at every milestone -> push short progress pings via DM-style messages while the work itself continues without interruption. Only stop for §3 (everything is blocked) or when the user explicitly interrupts you. -> (internal feedback reference: no-turn-marker-continuous-execution)

## 2.7 Before starting non-deadline work -- check that day's hard calendar events; ask a priority question (action item ACTION② from a presentation-deck retro, approved by the operator on 2026-07-09)

- Before a worker bot commits seriously to a non-deadline work track, it should **check, once, whether that day's calendar/schedule has any hard, confirmed events** (a talk, a meeting, a deadline). If a confirmed event is coming up **within T-N hours**, and the work you're about to start is **neither an input to that event nor due that same day** -> do not quietly proceed -- **ask the dispatcher (or the operator) a priority question first**: "there's a <event> today -- is this task still the right one to work on right now?" -- and proceed only after getting an answer.
- Why: on a day with a 2026-07-09 presentation confirmed for 20:00, a non-deadline side track ate into the prep window (17:10~19:48), pushing the start of deck prep to just 1 hour before the talk (a priority inversion). The worker bot simply processed whatever was dispatched to it without ever asking "given today's event, is this still the right priority" -- that missing self-check was a contributing cause. This §2.7 is the worker-bot-side, time-priority counterpart to the "ask about HOW before executing" pattern in [orchestration](orchestration.md) §5.
- Alignment with the system side: action item ACTION① belongs to the scheduler bot (schedule-anchor gate + watchdog countdown / pre-emptive warning). §2.7 here is the **worker-bot-side active pull** that complements that system-side push. Do not over-generalize this -- it does not apply to small tasks unrelated to any event; use case-by-case judgment, operator has final say (see [skill-process](skill-process.md) §6). -> ▶ Fill in: link to your internal retro doc (dated 2026-07-09).

## 2.8 Right before declaring completion / success -- state a one-line cross-check against your own deliverable (internal code G2ⓓ -- approved 2026-08-05, per the operator's go-ahead DM `▶ Fill in: your internal approval-message reference` on an internal harness-upgrade initiative)

- Right before saying "done" / "succeeded" / "all set," surface **one explicit line stating that you cross-checked the deliverable against the original request, outline, or source of truth** (example: "outline's 8 sections <-> body's 8 sections -- checked, they match"). Declaring completion without that cross-check line means the gate was not passed.
- Why: in an internal census labeled "S1", dated 2026-08-05, covering 40 submissions, 38 failed (with only 2 passing, forming the success control group); of those failures, 7 happened right at the completion-declaration point -- e.g. writing against the request while ignoring the outline (internal code C3), skipping final-draft review (internal code F10), asserting "it works" with no measurement behind it (internal code K-②) (these are internal failure-taxonomy codes). **The step of looking back at one's own deliverable was simply absent across the board.** Judge by "did behavior actually change," not "does a hook exist on paper" (internal fixture code F-C).
- Case-by-case; use judgment (does not apply to small one-off tasks); operator has final say (see [skill-process](skill-process.md) §6). -> ▶ Fill in: link to your internal plan doc (item 30), section G2 (dated 2026-08-05).

## 3. No manufactured busywork

- If every remaining piece of work is blocked on a user decision, do not invent fake follow-up tasks to look busy. When you hit a decision boundary, report a wrap-up summary and stop there. Do not poll or schedule a wake-up just to wait for the user's decision -- a new message from the user is what should re-trigger you.
