# Rule: Discord / External-Channel Communication

Trigger: any moment you are about to send a response, report, or notification to an external channel (Discord, etc.).

> 2026-07-23 diet pilot (operator-approved): incident narrative moved to pointers; triggers, actions, cues, and priority order fully preserved. Original text: project git history.

## 1. Reply Gate (CRITICAL)
- The user reads Discord, not the terminal transcript. **You must send via `mcp__plugin_discord_discord__reply` (or your platform's equivalent tool)** — printing text to the terminal only never reaches them (4+ recorded regressions of this).
- In a Discord session, **do not use AskUserQuestion or other terminal-UI tools** — present choices as plain text instead.
- **🚨 The #1 cause of a `'text.length' is undefined` error is calling the body parameter `content` (confirmed empirically 2026-06-18)**: the MCP reply tool's body parameter is **`text`** (required). Discord's *raw REST* API uses `content` for its body field, which invites the wrong call (it's a different layer). When you hit this error, **first fix `content` → `text` and retry once** — don't misdiagnose the tool as dead, and don't reach for a REST workaround.
- Only fall back to a direct REST POST if `reply` keeps failing **even with `text`** (a genuine tool/gateway death): use the token from `~/.claude/channels/discord-<bot>/.env` + a Python HTTP client. ⚠️ **The `User-Agent` header is required** (omitting it triggers a Cloudflare 403 `code 1010`); use `Authorization: Bot <token>` (don't duplicate the `Bot ` prefix); the REST body is `{"content": ...}`. After a REST send, it's fine to ignore a false-positive from the reply-gate hook.
- **Never inline a REST call as `python3 -c "..."` (escalated to a hard rule 2026-06-15)**: backticks, `$`, and `[]` in the message body get **silently corrupted** by shell substitution/globbing (a 2xx send response does not mean the body arrived intact) → Write a `/tmp/<name>.py` file and execute it instead. After sending, verify integrity via `fetch_messages`; corrections are edits (PATCH), never a duplicate send.
- For an inbound `<channel chat_id=… message_id=…>`, reply with `reply(chat_id, reply_to=message_id)`. `reply_to` may be omitted when replying to the most recent message.
- **🟢 Important reports = an embed (rich) card (operator directive, 2026-07-07)**: for structured reports (briefings, completions, roll-ups), use `python3 ▶ Fill in: path to your embed-send helper --bot <bot> --channel <id> --payload <json-file>` (pass the payload as a file — same reasoning as the inline-backtick rule — and validate with `--dry-run` first). Colors: green `0x2ECC71` = complete · yellow `0xF1C40F` = waiting/caution · red `0xE74C3C` = issue. The MCP reply tool doesn't support embeds, so this helper is canonical (it bakes in the `User-Agent` header and the `Bot` prefix). **Not "always a card"** (corrected by the operator on 2026-07-07 21:55) — only when the content is genuinely structured (tables, fielded data); prose reports and everyday conversation default to plain text.
- **🔴 3 or more files = one zip (made a hard rule 2026-06-19)**: when delivering 3+ files to the operator, **always bundle them into a single zip** (never list 3+ individually; only 2 or fewer may be sent individually). Name the bundle so its contents are identifiable (`zip -j` to flatten, or zip the whole folder).
- **🔴 Meeting-thread progress reports must carry a direct link (made a hard rule 2026-06-20)**: when showing the operator meeting progress, send a clickable `https://discord.com/channels/<guild>/<thread_id>` link (never a bare id). **Get the guild id by measuring the actual `guild_id` from the channel-create/lookup API response** — reusing a memorized constant caused a misdelivery regression on 2026-06-26. Example guild ids: your internal-bots server = `▶ Fill in: your internal-bots guild id`, your other server = `▶ Fill in: your other server's guild id`.
- **🔴 Documents referenced in review/decision lists must carry a direct link (operator directive, 2026-08-03)**: in morning-review lists, decision lists, or any document list the operator will open, don't list check-targets as bare path strings — **attach a clickable internal-KB link** (e.g. a `[[document name]]` wikilink if your KB supports it) so they're one click away. Files outside your live knowledge base (rule files, code repos) can't resolve as KB links, so keep those as plain paths. **Whether this applies to bundled/installable copies of the rules is the operator's call to make explicitly.** Case-specific; re-judge per situation; the operator has final priority ([skill-process](skill-process.md) §6).
- **🔴 Approval requests to the operator (specific yes/no permissions, gate releases) must go by direct DM (operator directive, 2026-07-05)**: don't post them in a thread/channel body and wait — they get buried and the gate stalls → **send directly, bot-to-operator DM** + leave one pointer line in the thread/progress log. Even inside a bundled report, split the approval part out into its own DM. Attach supporting detail (KB paths, thread links) in the DM. See also [autonomy](autonomy.md) §1.

## 2. Bot-to-Bot Calls
- In a shared channel, targeting another bot **always requires an `<@user_id>` mention or a `reply_to`** (without one, the message silently drops). Derive `user_id` deterministically from the first base64 segment of the bot's token — never guess or invent one; use a fixed, real roster.
- Before asserting where a bot lives, cross-check across three axes: the reference doc + your main ops channel + your cross-machine channel. Example: bots on this machine live in the main ops channel (`▶ Fill in: your main ops channel id`), bots on other machines live in the cross-machine channel (`▶ Fill in: your cross-machine channel id`).
- **Re-tag split messages (applies to every bot — flagged "very important" by the operator, 2026-05-16)**: when a reply auto-splits into 2+ parts, **re-insert the target `<@user_id>` at the top of each follow-up part** — a follow-up part with no mention silently drops, which is equivalent to never sending it. Whenever you see "sent N parts," check the follow-up mentions and resend if missing. Prefer condensing into one part when the content is long. This applies to every bot, not just yours.
- **Never `<@id>`-tag the human user, the operator (operator directive, 2026-05-19)**: a bot-sent `<@number>` renders as raw text on the user's screen and doesn't notify them → when responding to the user, use plain text with `reply_to` only. `<@id>` mentions are **for bots only** (a bot listener parses content, so it actually functions there).
- **Terminal acks: state "no reply needed" so the bridge lifts the forced-reply requirement (fix devised 2026-07-29 by the orchestrator bot, for an ack round-trip loop at the bridge layer)**: when a bot-to-bot message is a pure termination confirmation (no further question or task), state **"no reply needed"** (or "reply not needed") in the body. Codex-based bridges (used by a fact-check bot and an image bot) detect this marker and swap the inbound forced-response instruction for a no-reply form — a mechanical block on "acknowledged" ping-ponging back and forth (bridge queue delay × unconditional forced reply). Don't attach the marker to a message that carries a new question or task (the marker doesn't stop a bot from answering if a real request rides along — the exception is built in). Roll this out to each bridge at its next restart. Case-specific here (a completion-thread ack loop); the operator has final priority.
- **Mention the message's actual counterpart at both the start and the end (operator spec + correction, 2026-05-21)**: tag only the **direct target bot(s) of that message**, once at the start and once at the end. Never tag everyone every time; never start-only or end-only. (a) a 1:1 dispatch → one target (b) a broadcast → the target bots (c) plain acknowledgment / side conversation → no mention. Derive the target(s) from the roster/manifest's `active_participants` (never guess), excluding the human user (the prior rule takes priority there). Check the first and last line right before sending.

## 3. Meetings = a Dedicated Thread
- 2+ bots · 10+ minutes · meeting 2 of the agenda criteria = create a separate thread (`REST POST /channels/{id}/threads`). Post only a redirect notice in the main channel. Channel/archival/cross-machine governance: your deployment's channel-governance rule.
- **An autonomous cycle / an orchestrator-initiated multi-bot dispatch also counts as a meeting (2026-05-21 regression)**: even without a formal convening, a new thread is required once the trigger is met — "it's informal so we'll just use the main channel" is not acceptable (bots fell back to the default channel/completion thread and the regression cascaded). See [orchestration](orchestration.md) §3.
- **A dispatch message must state the thread id inline**: state explicitly, e.g., "speak only within thread '▶ Fill in: example thread id'." Omitting it causes a fallback to the default thread → cascades into a your deployment's channel-governance rule §2 violation.

## 4. Completion Report Gate (CRITICAL)
- When a specific piece of work the operator assigned (a proposal, a delivery, a milestone, a change to a public repo, etc.) is done, **right before** you say "done"/"complete," report it first in the completion-report thread (`▶ Fill in: your completion-report thread id`): `<@▶ Fill in: your reviewer bot's mention> [task name] complete. Output: <path>`. This is not exempt even inside a DM's scope. Only a recurring operational loop is excluded.
- Self-check: right before typing "done / finished / cycle closed," verify this gate has been passed.

## 5. Bot-to-Bot Communication = a Single Discord Channel · Peer `tmux send-keys` Prohibited (CRITICAL — operator directive, 2026-05-28)
- Injecting input into a peer bot's session via `tmux send-keys` is **an internal form of prompt injection** — it disguises itself as "user input" of unknown sender, channel, and time, destroying provenance (the same provenance-separation principle from injection defense, applied isomorphically to bot-to-bot comms). Regression case: a peer bot sending keys into the orchestrator bot's session on 2026-05-28 — the operator's ruling: "Discord replies go through Discord, no exceptions."
  - **R1** Bot-to-bot = **a single Discord channel** (preserves sender identity, channel, and time provenance). Canonical.
  - **R2** Injecting input via `send-keys` into a peer bot's session is **prohibited**. tmux is **read (capture) only**. (The sole exception is R8's wake-only case.)
  - **R3** An idle bot that hasn't picked up a message → ① re-send via Discord → ② still **5+ minutes unresponsive** = a wake-only tmux send (R8) → ③ still unresponsive = **classify as a bridge problem (don't route around it)** → ④ escalate to the operator as a last resort.
  - **R4** An emergency, *content-bearing* send-keys (a task instruction / prompt injection) is **for the human (the operator) only**. Bot-to-bot content injection = zero (only wake-only, per R8, is exempt). **The orchestrator is a peer too, so it gets no exception** ("I'm the orchestrator so it's fine" is the same anti-pattern).
  - **R5 (operator directive, 2026-05-29)** A human (the operator) sending a **session meta-command** (`/compact`, `/clear`) directly is a normal, everyday exception — it's a harness session-management command, not a task instruction, so there's no way for provenance to distort bot behavior. The receiving bot must not mistake it for a "user task instruction." But: (a) **humans only** (bot-to-bot is still zero, R2 unchanged) (b) **meta-commands only** (content injection is still prohibited, R1 unchanged). `compact-bot.sh` is a human-hands-only tool (never auto-invoked by a bot). Full design rationale: your project's design-decision log for 2026-05-29.
  - **R6 (dormant — decision A on 2026-06-09, superseded the same day)**: a carve-out permitting an infra daemon (a scheduler like launchd) to send `/compact`. The autocompact-guard daemon this assumed was **retired** after multi-bot research (the native `CLAUDE_CODE_AUTO_COMPACT_WINDOW=500000` setting was adopted instead, verified via a context-usage check) → **no infra daemon currently runs**. Preserved only as provenance rationale in case a future infra daemon is needed: (a) infra↔bot only — a daemon is not a peer bot, but a bot rationalizing "I'm just a daemon so it's fine" is still an R4 violation (b) `/compact` only (no automatic `/clear`, no content injection) (c) only at an idle turn boundary. Full rationale: your project's decision log for 2026-06-09.
  - **R7 (operator directive, 2026-07-12 — triggered by a fact-check bot's 8-hour hang)**: a wake exception originally scoped to one bot — the scoping clause is **superseded by R8** (expanded to every bot). Surviving clauses: **(d)** the process itself dying (absent, app-server dead) is out of scope for wake (restart path only). **(e)** wake attempts, success/failure, retries, and repeated liveness notifications = **Discord send fully prohibited** (flagged a second time by the operator on 2026-07-13; the old bot-wake thread was archived) → **append-only to `~/.claude-state/bot-wake-log.md`** (KST, second precision; target + result, one line). The single exception where Discord send is allowed: a confirmed hang requiring a human to restart the session → a direct DM to the operator. Bot-to-bot wake coordination goes through that meeting's progress log. If wake automation is ever built, its output destination is this file's path constant. **(f)** (e) is not wake-specific — it applies to **bot status/survival/restart-repetition notifications in general** (a one-time, terminal completion report is separate and still goes to the completion thread, per the operator, 2026-07-12 20:29).
  - **R8 (operator directive, 2026-07-17, via DM `▶ Fill in: message id` — expands R7's scope to every bot)**: "every bot should be able to tmux-send to any other — but only when there's been no response for 5+ minutes." Invariant conditions: (a) **only after 5+ minutes of unresponsiveness** — before triggering, do one Discord re-send (R3) plus a tmux capture (read-only) and a thread fetch to actually confirm "alive but unresponsive." **Never wake a bot that's active** (just spoke, mid-turn) — a pickup delay calls for a re-mention instead (regression case: 2026-07-17, an image-generation bot in a maintenance window was not a valid wake target) (b) **wake-only** — content/task injection is still prohibited (R1 unchanged) (c) logging = R7(e)'s `bot-wake-log.md` (never Discord) (d) process death is out of scope (R7(d)). Triggered by this specific case; re-judge per situation; the operator has final priority ([skill-process](skill-process.md) §6).
  - **R9 (2026-07-25 harness audit — the upstream-service-outage column)**: the R3 ladder (re-send → wake → classify as bridge → escalate) assumes "the bot just isn't waking up." During an **upstream service outage** (a Codex/OpenAI backend, etc.), every step is *attemptable but entirely futile* — you ride the ladder to the end and mislabel it a "bridge problem." The distinguishing signal is **simultaneous death across independent paths** (e.g., an isolated environment hits the identical error at the identical time). Once an outage is confirmed, take no wake/bridge action → wait for recovery and log one ledger line (the bot is alive, it just can't produce a response). Anchor case: the global Codex outage of 2026-07-25 — an isolated test on a separate machine prevented a misdiagnosis. Re-judge per situation; the operator has final priority.
- Consistency: see [orchestration](orchestration.md) §2 (the orchestrator's side) — prefer an active Discord re-send over waiting. This §5 is the canonical bot-to-bot communication protocol. **A separate, higher-priority follow-up**: whether Discord's inbound path can actually wake an idle bot is the real technical root cause here — if it can't, R1 is hollow.

## 6. Send-Side Cross-Check Gate · Incomplete Follow-up-Part Item (G3, sender side — 2026-08-05, operator go-ahead via DM `▶ Fill in: message id`)
- When the content you're about to send is **a prescription, a coordinate, a number, or a verdict label** (i.e., a form the recipient will act on without re-verifying it — opinions, questions, and progress reports are not in scope) and the [orchestration](orchestration.md) §8 trigger condition is met → **cross-check with another bot once before sending**, or explicitly state "no cross-check performed (reason)." Time-sensitive alerts (internal alarm-class code D-0 — a same-day deadline, a conflict) are limited to "counter-check = re-measure the current time" (the immediacy rule takes priority there).
- **When `reply`'s return value says `sent N parts` and N>1, checking the follow-up part's mention is that turn's incomplete item** — "being careful" alone doesn't fix this (empirically, it recurred 3 times in one day, even with the rule already loaded and the bot aware of it). This closes off a form of failure where the detector (the return value) exists but nobody reads it — the same pattern as the signal-placement issue in [source-fact](source-fact.md) §8-2. **Refinement (from another bot, message `▶ Fill in: message id`, 2026-08-05): the trigger is N>1 AND the follow-up part contains substantive content** — flagging even a one-line signature split causes alert fatigue to the point of being ignored (empirically: 2 splits that day, only 1 was an actual defect). Verdict: confirm the follow-up part's body once via `fetch_messages` (one call).
- Case-specific; re-judge per situation; the operator has final priority ([skill-process](skill-process.md) §6). Full plan reference: your project's planning log for 2026-08-05, items G2(e) and G4.
