# Rule: Skill & Process Discipline

Trigger: starting a build/design task ("let's build X"), a bug/debugging task, or a verification task; an experimental autonomous loop; delegating work to a subagent.

If a skill is even 1% applicable, invoke it. Priority order: process skill first → implementation skill second. On conflict: **explicit user instruction > skill > default behavior**.

- **A designated/commissioned skill or tool = stay inside its process, no silent departure** (operator, 2026-07-19 — regression: a commissioned tool's output was discarded without authorization): if a designated tool's output is rejected, the first-line fix is "how do we use that same tool differently" — rejection is usually about content, not tool choice. ## 1.5 Live spec updates (P1 — pattern #2 from an internal review round)
- A scope change mid-execution (new inbound request, added instruction, a peer's report) = **in that same turn**: (i) atomically patch the spec file (e.g. a `01-spec`-style document) (ii) re-dispatch in the same turn (changed paragraph + timestamp, consistent with [orchestration](orchestration.md) §5) (iii) log one scope-delta line in the progress file (e.g. `02-progress`). A spec is a living document — "I'll fold that in once this is done" is where drift starts.
- Self-check: the thought "I'll update the spec later" is exactly the moment to patch it now. Room for re-judgment, operator has final say (§6).

## 1.6 Solo-work planning = document it, then keep re-reading it (operator, 2026-07-26 02:10 — "I lose my way when I'm working solo")
- Why: in a meeting, the progress file is the context anchor — but **solo work has no anchor**. If the plan only lives in an (ephemeral) response, purpose drifts and scope creeps (observed 2026-07-25 00:52).
- Principle for a non-trivial solo task: (i) generate the plan via your prompt skill (AUTO mode) or the named pipeline (§1) (ii) **pin it to a file** — inside a meeting/work-log context, a numbered document in that folder; outside one, your specs/records location (iii) **re-read and cross-check it at every milestone or direction change** (iv) scope changes follow §1.5 as written.
- Self-check: the moment you think "what was I about to do next," or you're about to tack on a step that wasn't in the plan, is the re-read trigger. Small one-off tasks are exempt; operator has final say (§6). Landing convention: see your harness-audit design document (2026-07-25, item #73).

## 1.7 Auxiliary-measurement / refinement-loop gate (operator, 2026-08-02, directive "proceed only through gate (ii)" — regression in an exposure-counting loop)
- Why: **every individual finding can be genuinely true and the loop can still be a failure.** When an auxiliary measurement (a supporting metric built in service of the real deliverable) develops its own quality bar and enters a mutual-refinement loop with itself, it consumes the real deliverable. The failure is invisible at the action layer — it only shows up at the **aggregate layer** (cumulative cost vs. zero contribution to the final output) — so the existing gate (the pipeline end-time rule in §1, which only covers that one pipeline) didn't catch it. Regression: 2026-08-02, an exposure-counting-loop calibration — three separate exposure-counters spent a round cross-verifying each other and grinding through defect candidates while the final report's conclusion sentence never changed; the operator had to step in twice ("why isn't this ever going to finish?").
- **(i) Conclusion-delta gate (judge layer)**: before attaching a 3rd round of judgment/dispatch to the same auxiliary track, a mandatory one-line self-check is required — "what sentence or number in the **final deliverable** does this finding change?" If the answer is "none — it only improves precision, labeling, or coverage," pin the current value as a lower-bound label and close the track. The question is about **reach**, not whether the finding is true.
- **(ii) Auxiliary-measurement budget (track-opening layer)**: at the moment you open an auxiliary-measurement track, state in the progress file (outside a meeting: the spec file): (a) a **round cap** (example: 3 round-trips) and (b) a one-line **"good enough" criterion**. Hitting the cap = pin the current value as a lower-bound label + auto-close. Extension only if the (i) conclusion-delta check passes.
- **(iii) Mechanized layer — not adopted**: a watchdog that detects N round-trips plus an unchanged goal sentence was **not adopted** (operator, 2026-08-02: "proceed only through gate (ii)").
- Case-specific basis, room for situational re-judgment, operator has final say (§6). Subject to sync across your deployed harness copies — see [porting-infra](porting-infra.md). (Source discussion dated 2026-07-30; see your incident log.)

## 3. systematic-debugging Iron Law
- No fix before root cause is established. Four phases. Can't reproduce = no guessing, and **no phantom fixes**. If the user says "that's not it" or "it's older than that," re-enter Phase 1. Even an inherited hypothesis must be verified against the actual file before you act on it.
- 3+ failed fixes = suspect the architecture (Phase 4.5) — stop patching and go discuss it instead.

## 4. Autonomous research loop
- One-shot runs are unbounded (manual stop). Sustained runs auto-terminate on convergence (streak ≥ 8) (▶ Fill in: your autonomous-research-loop skill). Only ever modifies a single target file; keep an improvement, discard a regression; log every experiment (results.tsv + results.jsonl). Report completion through your completion-report thread/gate.
- **Diversity check immediately before auto-terminating on convergence** (2026-06-14, a mutation-convergence incident): right before stopping, check skeleton-duplication rate once — the unique-hash rate among accepted mutation skeletons (low = suspect an attractor) — with self-loop rate as a secondary signal. If the skeleton is identical and only leaf values are being swapped, inject one cross-model or "unstuck" variation and re-judge. This confirmation gate is not automatic — the bot judges it.

## 5. Delegation boundaries
- **Read-only Task subagents** (a subagent given write access is a false-completion bug waiting to happen). **Agent Teams members can write** (they run as independent processes). Always verify a subagent's result before using it.
- **Confabulation-rate smell** (pattern #4 from an internal review round): before accepting a subagent's output, watch for an abnormal ratio of tool calls to citations (example: 4 calls in 40 seconds producing 10 cited sources) — that's grounds to suspect fabricated citations; re-run under a real-source constraint, or verify directly. This is a rule of thumb, not a fixed threshold.

## 6. Case feedback → rule/skill hardening: no over-generalization (operator correction, 2026-06-11; promoted at cycle-02)
- Do not over-generalize case-specific feedback into a universal "must/never." Hardening a rule requires all three elements: (i) an "in this particular case" qualifier (ii) room for situational re-judgment (iii) **the operator's latest feedback always wins**.
- This is the "commit it to a rule/skill file" analog of the pre-response lint that flags absolute words ("always," "must," "never," "forbidden"). Regression: 2026-06-11, a layout was hardened as "permanently deprecated" in a rule file, and the operator corrected it: "it depends on the situation."
