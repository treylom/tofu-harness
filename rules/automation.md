# Rule: shipping automations that other things depend on

Trigger: you are about to deploy or modify a watcher / liveness monitor / matcher over other agents' output, or to write a status field, marker, or structured value that some other automation reads.

- **Self-test a watcher against real data variants before it goes live.** *(mined 2026-07-12 — 5 incidents, 3 with filed bug reports)* A monitor that matches other agents' output must be run, before deployment, against every known format variant of the real data (Korean/English display names, date-prefixed timestamps, renamed keys). Two separate false-stale storms came from a regex that didn't know one legitimate timestamp format. Also: exclude the operator itself from its own watch list, and prove — by running it — that every state that should be silent (completed, blocked, terminated) actually produces zero output. A terminated meeting once got a public progress ping every interval, forever.
- **A value someone else reads is a contract; check the reader, not your memory.** *(mined 2026-07-12 — 4 incidents, incl. a 128-reinjection loop)* When you write or change a status field, completion marker, frontmatter key, or any structured value that a watchdog, parser, gate, or template consumes, open the consumer's code or spec right after writing and confirm the field name, markup, and format match what it actually reads. The worst case on record: a completion record written with the wrong field name was invisible to the scheduler reading it, which re-injected the "unfinished" task 128 times.
- **A value replicated across consumer-specific surfaces dies on the surface you don't know about.** *(mined 2026-07-29 — 3 instances in one day)* When the same value (a version, a model ID, a config knob) lives on N surfaces each read by a different consumer, "updating it" means updating all N — and the failure mode is that the update routine knows only some of them. One day produced three instances of the same shape: a plugin version bumped 5 releases on one manifest while the second manifest — the one the other runtime actually reads — stayed 5 behind; a launcher script whose comment said "identical to the shell function" after it had silently diverged from the shell function actually used at startup; and the audit's own design doc naming the stale mirror as the source of truth, nearly becoming surface #4. Fixes: keep an explicit list of every surface a replicated value lives on, add a mechanical cross-check that sweeps them all (a `--check-versions`-style command beats memory), and before repairing "the" surface, verify it is the one the consumer actually reads — otherwise the repair is a phantom fix with a misleading "fixed" record on top.
- **Register session-wide hooks globally; a project-root Stop hook never reaches sub-working-directory sessions.** *(mined 2026-07-29 — measured from both directions)* A hook registered in a project root's settings does not fire for agents whose working directory is a subdirectory with its own settings file — measured as zero invocations from the sub-WD side, and confirmed from the other side by a globally-registered hook firing fine in the same sessions. If a hook must fire for *every* session (compact protection, completion gates), it belongs in the global settings layer, fail-open. Corollary for canaries: a hook that logs only when it blocks makes "zero log lines" unreadable — you cannot tell *not running* from *ran and passed*. Log an "invoked" line before any condition check, so zero splits into its two faces.
