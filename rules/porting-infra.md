# Rule: Porting, Deployment & Infrastructure

Trigger: porting a tool/plugin/skill to another platform, "deploy/push", adding an MCP server, writing API code.

## 1. Check the Upstream Repo Before Porting (CRITICAL)
- Before hand-rolling a workaround (a self-made bypass such as a symlink, etc.), **check the upstream repo first**: platform packaging conventions (`.codex-plugin/`, `.cursor-plugin/`, `.opencode/`), `sync-to-*` scripts, AGENTS.md/GEMINI.md, README multi-harness install matrices. Upstream has usually already solved this.
- Verify with: `gh api repos/<o>/<r>/contents`, and grep the README's install section. A hand-rolled workaround should be demoted to "fallback for when there's no upstream packaging for this platform" only. Cite the source (file:line / GitHub link) with a SOURCE FACT label.
- Example: a skill plugin (e.g. `obra/superpowers`) already ships a `.codex-plugin/plugin.json` that's registered with the official Codex marketplace (`openai/plugins`, i.e. the reserved `openai-curated` namespace). Non-interactive install = set `[plugins."<name>@openai-curated"] enabled=true` in `config.toml` → the app-server materializes it at `~/.codex/plugins/cache/openai-curated/<name>` on startup.

## 2. Deployment Sync

▶ Fill in: the names/paths of your deployment bundle repos (this rule assumes exactly 2) and the secret-token regex pattern(s) you want the pre-push scan to use.

- Whenever you detect "deploy"/"push", sync **both of your deployment bundle repos** (2 repos total) — not just one. See your repo-ops hub/skill for the deployment-sync procedure, if you maintain one.
- Before pushing, scan for secrets — example pattern: `grep -rn "ntn_[a-zA-Z0-9]" --include="*.md" . | grep -v "ntn_xxx"` (adapt the token prefix to whatever secret formats you actually use). A public-repo change falls under the confirm-exception in [autonomy](autonomy.md) §1.
- **On every public-repo push, also check that the GitHub "About" field is still in sync (incident: 2026-07-16 — the operator caught a public repo whose About/description hadn't been updated after a README change to the model-lineup/coverage wording)**: if a README or skill update changes **model-lineup or coverage wording**, update that repo's About (description + topics) in the same session with `gh repo edit --description` — About is a search/first-impression surface, and letting it drift from the README is stale advertising. Judge case by case; the operator's call wins on close calls ([skill-process](skill-process.md) §6).
- **Mandatory green smoke check before pushing to either deployment bundle (standing instruction, 2026-05-29 — "test this every time")**: before pushing, run each bundle's smoke check (e.g. `thiscodex smoke` for one bundle, and the other bundle's equivalent) and confirm green. On failure, either hold the push, or explicitly note the failure's cause/irrelevance and then decide — even a pre-existing, unrelated failure must be caught before push (case: on 2026-05-29 an installer function, `choose_install_surface`, once stalled a smoke run on an always-on (`when:always`) interactive prompt, and only the pre-push smoke check caught it).
- **Changes to your bot operating rules/policy = sync into your deployment bundle(s) by end of session (standing instruction, 2026-06-03)**: if you changed the operating rules (this rules directory, or related operating policy), sync a generalized version of that change into your deployment bundle(s) (the rules-system copies) **before the session ends** — run the secret scan and smoke check first, then push. Skipping this lets your deployed bundles drift from your canonical rules. Self-check: any session in which you Write/Edit a rule file should end with a "does this need a deploy-bundle sync?" check. Conflict priority: explicit user instruction > rule > default.
  - **"Changed" includes corrections and retractions, not just additions (incident: 2026-07-26 — a 12-hour stale-copy regression)**: a rule's already-shipped bundle copy is a *citation* of that rule — if the rule is later corrected or retracted, that copy is also due for a re-sync (the deployment-bundle counterpart of "a correction must be traced back to every place it was cited," [source-fact](source-fact.md) §7). **Syncing a correction/retraction takes priority over syncing a brand-new addition** — an unsynced new rule just leaves the bundle less complete, but an unsynced retraction means the bundle is *actively shipping a claim that's already been withdrawn* (a different severity class). Incident timeline: a change synced at 21:32 on 2026-07-25 was retracted at the source at 05:22 the next morning, and the bundle copy sat stale for 12 hours, publicly exposing the retracted claim the whole time. Judge case by case, situationally; the operator's call wins.
- **🚨 Independent review gate before deploying anything public (standing instruction, 2026-07-02 — "review should obviously be part of this")**: immediately before pushing/publishing a public repo, README, or deployment doc, **independent review is required** (from whoever owns copy/content quality on your team) across 4 axes: ① factual accuracy ② naturalness (strip translation-ese/stiffness and overstatement) ③ cross-language consistency (if you publish bilingual docs) ④ internal consistency. Report format: `file:line + issue + suggested fix` → apply the fixes → confirm the re-review diff is clean. No solo deploys. (This is orthogonal to the smoke check above — smoke checks functional-green, this gate checks copy/factual accuracy.) This is the public-deliverable analogue of the slide-deck 3-reviewer gate ([slide-deck](slide-deck.md) §2.5). **Incident**: on 2026-07-02 a public repo was deployed without review, and the operator personally caught a mis-description (a model described as an "instance nickname" instead of stating plainly that it was an actual model, plus an exaggerated "long in use" claim) — a follow-up 4-axis review then surfaced 6 more issues (🔴Critical: the write-up self-contradicted its own stated experiment conditions — "harness ON" vs. "vanilla" — undermining its core argument; 🟠 an inconsistent definition on one of its comparison axes; and others). Root cause: no review gate existed (knowing the rule ≠ enforcing it) plus a solo deploy. Self-check: right before pushing a public repo/doc, ask "did this get reviewed yet?"

## 3. MCP Servers
- Before adding a server, list your current ones (e.g. `claude mcp list`); after adding, run a health check. Remove immediately on connection failure. Maintain your own denylist for known-unreliable community MCP registries (e.g. `@smithery/cli`).

## 4. API Code
- When writing API code, look up current docs (Context7 MCP or your equivalent up-to-date-docs tool) first, and keep a copy of working examples in your repo if you maintain one. Model names = exactly what your agent docs/spec require (a plausible newer-than-your-training-cutoff model name is fine; substituting your own knowledge-cutoff-era model name instead of the current specified one is not).
